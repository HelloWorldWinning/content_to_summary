### PART 1. Author's Map（作者论证地图）

#### 1. Core Thesis（核心主张）
影响 AI 实际使用成本的主导因素并非大模型 API 的单价，而是智能体框架（Harness）对上下文与历史消息的管理效率（能效）；通过优化框架的调度机制或根据任务复杂度搭配轻重框架，可以在不牺牲任务完成度的前提下实现 40% 至 90% 的成本削减。

#### 2. Evidentiary Base（证据库）
*   **对比实验数据（硬数据/Composio 团队）**：相同模型（Kimi K3）跑同一批 28 个编程任务，不同框架（Kemi Code、Hermes、Claude Code）的成功率相近（22/21/20 个），但 Token 消耗中位数分别为 6.1 万、6.7 万与 34 万，最高相差 6 倍（极端场景差 30 倍），单任务成本相差近 10 倍（$0.22 vs $2.00）。
*   **日志分析证据（专家审计/Sebastian Raschka）**：对 Claude Code 的运行日志提取显示，输入 Token 与输出 Token 比例高达 128:1（输入 57.8 万 vs 输出 4500），证明 Token 膨胀绝非源于代码生成量大，而是框架在每一轮交互中全量回放历史记录（“翻旧账”）。
*   **编排层优化实验（硬数据/Ryther 公司）**：固定 6 个基础模型，仅将传统智能体循环（Loop）替换为优化后的 Harness 编排层，在 22 个企业级任务中实现平均成本降低 41%、延迟缩短 44%、Token 消耗减少 38%。
*   **行业先例（产业动态/DeepSeek）**：DeepSeek 发布的 Agent Spec v0.7 通过精简基础 Harness，直接降低了 65% 的输入 Token 消耗。
*   **直觉泵与类比（Intuition Pump）**：将模型比作汽车发动机/电费单价，将 Harness 比作变速箱/用电设备功率；强调“发动机再省油，变速箱漏油也白搭”。

#### 3. Logical Warrant（逻辑推导链路）
*   **大前提**：总使用成本 = API 单价 × Token 使用量。用户无法改变供应商的 API 单价，因此成本优化的唯一有效空间在于控制 Token 使用量。
*   **小前提**：Token 使用量的最大来源是 Harness 在多轮交互中重复喂入的上下文（系统提示词、工具定义、历史日志），且该消耗在传统 Loop 中呈接近二次方的积累趋势。
*   **结论**：改变 Harness 的上下文回放逻辑或换用轻量化 Harness，能直接从源头切断膨胀的输入 Token，从而以极低成本获得数量级的开销节省。

#### 4. Stated Scope（论证边界）
*   **适用场景**：日常脚本编写、单文件修改、轻量级编程任务及 90% 的日常简单 AI 交互（“感冒发烧”类任务）。
*   **显式例外**：作者承认在剩余 10% 的复杂架构重构、跨文件大改动（“疑难杂症”）中，全量历史上下文确实能提高稳定性与成功率。

#### 5. Implicit Opponent（隐性对手）
*   **观念一**：“降本只能靠等 API 降价或换用低质便宜模型”的直觉误区。
*   **观念二**：“Agent 消耗 Token 多是因为它思考深入、生成的代码量大”的错误归因。
*   **设计模式**：现阶段主流 Agent 框架“宁可多传一千，不可漏掉一个”、缺乏智能动态调度的粗放式设计。

#### 6. Intended Takeaway（预期行动转化）
*   **认知改变**：评估 AI 成本时，将注意力从“模型 API 价格表”转移到“框架 Context 管理效率”上。
*   **具体行动**：
    1. 简单任务用轻量框架，复杂任务才上重型框架（任务分流）；
    2. 频繁开辟新会话，避免长会话的历史堆积；
    3. 优先选择支持 Prompt 缓存（Prompt Caching）的框架；
    4. 为 Agent 配置硬性的轮次与预算上限；
    5. 主任务窗口严禁插入无关杂谈。

### PART 2. Hostile-But-Very-Fair REVIEW（批判性审阅）

#### 1. Steelman（强形式重述）
框架层（Harness）对上下文的粗暴回放确实构成了当前 Agent 基础设施中最严重的工程浪费。在多轮对话中，输入 Token 呈指数级累积，导致“输入/输出比”严重失衡。作者准确揭示了“框架税”这一被绝大多数开发者忽视的成本黑洞，并有力证明了仅仅优化编排层结构（如利用缓存、裁剪历史），就能在模型不变的前提下榨取出数倍的性价比。

#### 2. Weakest Link（最薄弱环节）
> **引用文本**：“看成功率 Kemi Code 28个里成功了22个 Hermes 21个 Claude Code 20个 差不太多 基本一个水平线 说明三个框架水平差不多”

*   **断裂点分析**：样本量仅为 28 个任务，在统计学上严重欠效力。更致命的是，评测未公布任务的复杂度梯度。如果这 28 个任务大多集中在“单文件修改”级别，轻量框架自然表现良好。然而，重型框架（如 Claude Code）牺牲 Token 换取的是在长链路、多文件依赖重构时的鲁棒性。用简单任务的成功率相近，来推导“三个框架水平差不多”，从而判定重型框架的消耗全都是“浪费”，存在严重的选择性偏差（Sampling Bias）。一旦面对超高难度任务，轻量框架的成功率可能会断崖式下跌。

#### 3. Evidence Audit（证据审计）
*   **利益相关方偏差（Conflict of Interest）**：作者引用的两个主要实验分别来自 **Composio**（Agent 工具集成商）和 **Ryther**（企业级 Agent 平台）。两家公司均有极其强烈的动机通过夸大现有主流框架（如 Claude Code）的低效，来推介自己的轻量化方案或优化编排产品。
*   **控制变量漏洞**：CodeX 与 Claude Code 的对比直接套用了 SWE-bench 榜单数据，但 SWE-bench 上的不同提交所使用的底层 Model 版本、系统 Prompt、Prompt Caching 命中状态均不一致，直接将单任务成本归因于 Harness 缺乏严格的控制变量控制。

#### 4. Hidden Premises（未声明前提）
*   **假设一：开发者具备预判任务复杂度的能力**。作者建议“简单任务用轻型框架，复杂任务用重型框架”。但 Agent 的核心价值正是在于替代人类处理不确定性。如果用户必须在执行前精确评估任务难度，这本身就引入了极高的认知负荷与操作成本。
*   **假设二：时间成本/人力成本低于 Token 成本**。框架节省 Token 往往意味着对上下文的截断或摘要，这必然增加模型丢弃隐式约束（Context Loss）的风险。如果因为上下文精简导致 Agent 在第 15 轮跑偏，开发者排查错误所浪费的工时成本，将远超省下的几美分 API 费用。

#### 5. The Blind Side（视角盲区）
*   **忽略 Prompt Caching 的经济学抵消**：作者虽然提到了 Prompt Caching，但未能意识到 Prompt Caching 已经从根本上改变了“翻旧账”的成本结构。在主流 API（如 Anthropic/DeepSeek）支持 90% 以上缓存折扣的背景下，全量回放 50 万 Token 的实际计费成本可能仅相当于 5 万 Token 未缓存的成本。这使得“输入 Token 堆积”在经济学上的危害被显著放大，框架层为了稳定性而回放上下文的策略在未来反而可能是性价比极高的选择。

#### 6. One Hit Kill（关键一击）
*   **致命追问**：如果在 SWE-bench Verified 或具备复杂多文件依赖的重度重构任务（非简单的 28 个测试集）上，剔除 Prompt Caching 折扣后，轻量框架（如 Hermes/Kemi）在保持与 Claude Code 同等成功率的前提下，是否还能维持 5 倍以上的成本优势？如果不能，所谓“6 倍到 30 倍的框架税”是否只是简单任务场景下的度量假象？

#### 7. What Would Settle It（最终检验方案）
设计一个大规模（>500 任务）、梯度涵盖轻度到超重度的双盲基准测试：
1. 强制在所有框架中开启统一的 Prompt Caching 策略；
2. 统计各框架在不同复杂度梯度下的 **“单次成功综合成本”**（包含失败重试成本与人工干预工时折算）；
3. 观察轻量 Harness 在高复杂度任务上的成功率衰减曲线，以此确定 Harness 上下文裁剪的真正安全边界。
