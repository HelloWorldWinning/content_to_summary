### PART 1. Author's Map

#### 1. Core Thesis（核心主张）
高效使用 Claude Code 等 AI 编程工具的核心不在于撰写冗长的 Prompt 或增加角色设定，而在于通过“4条编程规则”约束 AI 的行为边界，并结合“预先注入特定项目上下文（上下文优先级高于指令）”的方法来消除 AI 的错误假设与乱改行为。

#### 2. Evidentiary Base（论据支撑）
*   **专家证言（Expert Testimony）**：引用 AI 领域权威 Andrej Karpathy（OpenAI 初始成员、前特斯拉 AI 总监）的推文与实际工作流转变——其个人代码撰写比例在 2024 年 11 月至 12 月间从 80% 手写翻转为 80% AI 编写。
*   **开源既成事实（Historical/Community Precedent）**：某软件工程师将 Karpathy 总结的 3 大坑提炼为“4 条编程规则”，在 GitHub 上获得了超过 15 万 Star 的高度认可。
*   **个人实践经验（Anecdote/Case Study）**：作者一年间使用 Claude Code 运行 23 个小项目的亲身提感；以及上周给 Claude Code 明确需求却因缺乏项目上下文生成了“通用废话/标准答案”的反面案例。

#### 3. Logical Warrant（逻辑桥梁）
*   **权威引证与归纳推理**：顶尖 AI 专家（Karpathy）与开源社区（15万 Star 规则）共同证实了 AI 编程的三大本质痛点（默示假设、过度复杂、顺手乱改）；作者通过 23 个项目的实操归纳出：AI 产生垃圾代码的主要原因不是“指令（Prompt）不够细”，而是“AI 缺乏项目专属的上下文信息”。因此，只要在指令输入前强制 AI 读取结构化上下文（`CLAUDE.md` / `Index`），就能消除信息不对称，大幅提升产出质量。

#### 4. Stated Scope（明确边界）
*   **适用人群**：使用 Claude Code / AI 编程工具的专业工程师及单兵创业者（“一人公司”）。
*   **适用场景**：涉及多文件、有特定架构规范、状态管理与文件结构的真实项目开发；非简单单页演示代码。

#### 5. Implicit Opponent（隐性对手）
*   **“Prompt 提示词至上”论者**：认为 AI 写不好代码是因为提示词不够长、不够详尽或没有设定足够的 AI 角色（NPC）。
*   **“AI 编程无用论/未成熟论”者**：因遇到过 AI 乱改代码、写冗余代码而断定 AI 无法胜任复杂开发的人。

#### 6. Intended Takeaway（目标行动）
读者应改变使用 Claude Code 的习惯：不要直接输入长指令，而是先建立项目的 `CLAUDE.md` 文档和 Reference 索引文件夹，强制 AI 在执行任何编写指令前先吸收项目上下文，并严格遵循“先思考、简洁优先、外科手术式修改、目标驱动”四项原则。

### PART 2. Hostile-But-Very-Fair REVIEW

#### 1. Steelman（最强版本重构）
大模型具备极强的代码生成能力，但由于其概率生成特性，极易在无约束状态下产生冗余设计和隐式破坏（修改无关代码）。通过“4条精细化控制规则”（限制修改范围与复杂度）结合“项目专属上下文预加载机制”（`CLAUDE.md` 索引），本质上是为 AI 搭建一套高精度的沙箱和系统指南，将大模型的随机性严格限定在既定架构内，从而实现真正的单人高倍率生产力爆发。

#### 2. Weakest Link（最薄弱环节）
> **最薄弱假设**：“只要在项目开始前让 AI 读取 `CLAUDE.md` 和 `Index`，AI 就能准确吸收并严格执行特定项目的上下文约束。”

*   **失效分析**：该论断忽视了大模型的“注意力衰减”与“中间迷失（Lost in the Middle）”现象。随着项目规模扩大，`CLAUDE.md` 和索引文件必然膨胀，AI 在处理长上下文时依然会遗漏关键约束，甚至将过期的上下文与新指令混淆。一旦项目跨越单人小项目的临界点，维护一套“能让 AI 完美理解的上下文索引”所付出的认知成本，可能会迅速超过手动重构代码的成本。

#### 3. Evidence Audit（证据审查）
*   **光环效应与社会认同（Social Proof Bias）**：作者大量借用 Karpathy 的个人履历（OpenAI、特斯拉、15万 Star）来为自己的观点背书。然而 Karpathy 表达的是对大模型能力跃迁的感叹，并非直接证明“写 `CLAUDE.md` 上下文是解决一切问题的唯一解”。
*   **样本选择偏差（Selection Bias）**：作者的经验来自于“23个小项目”。小项目的上下文极其简单且容易被单个 MD 文件覆盖。在大型遗留系统（Legacy Codebase）、高并发或高度解耦的微服务体系中，这种“预先读一点 Context 就能解决问题”的经验缺乏代表性。

#### 4. Hidden Premises（隐藏前提）
1.  **假设开发者本身具备极高的架构设计能力**：作者提到“大模型能力强时，需要依靠专业能力做到”。如果开发者自身无法写出结构清晰、边界明确的 `CLAUDE.md` 和 `Index`，AI 读取上下文后依然会给出混乱的答案。
2.  **假设 Token 成本与上下文加载延迟可以忽略不计**：强制 AI 每次运行都读取全局索引和 Reference 文件夹，会显著增加 API 调用开销与交互等待时间。

#### 5. The Blind Side（盲区与忽视的视角）
*   **架构演进的动态冲突**：强制 AI 严格遵循旧有的 `CLAUDE.md` 和 `Index` 规范，会导致 AI 在开发新功能时陷入“过度防御”，无法提出更优的架构重构方案。
*   **工程团队协同的真实困境**：单人公司（一人公司）可以随意更新 `CLAUDE.md`，但在多程序员协作项目中，AI 上下文文件的版本控制、冲突解决和标准统一是极难处理的工程难题。

#### 6. One Hit Kill（致命一问）
> 如果把开发场景从你擅长的“单人 23 个小项目”，切换到拥有 100 万行代码、30 人协同维护且缺乏文档的旧项目，**你这套依靠个人编写 `CLAUDE.md` 和强制全局 Index 的上下文预加载策略，如何在不触发 Token 溢出和上下文迷失的前提下依然有效？**

#### 7. What Would Settle It（判定性检验标准）
在一个包含 50+ 模块、多层依赖的开源项目上进行 A/B 测试：
*   **对照组 A**：仅使用长 Prompt 指令，不预加载全局 `CLAUDE.md` 上下文。
*   **实验组 B**：完全按照作者建议，建立 `CLAUDE.md`、Reference 文件夹与 Index，强制 AI 每次运行先读取。
*   **衡量指标**：对比两组在完成同一批复杂重构任务时的 **一次性编译通过率**、**无关函数破坏率（Bug数）**、**开发者整体消耗时间（包含维护 MD 文件的时间）** 以及 **Token 总开销**。
